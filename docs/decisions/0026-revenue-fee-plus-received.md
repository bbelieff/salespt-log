# ADR-0026 — 매출 = 수임료 + 수납액 (승인총액은 기록용, 매출 제외)

> **📄 이 문서는 무엇인가요?**
> - **한 줄 요약**: 매출의 불변 정의를 박제 — 매출 = 수임료 + 실제 수령 수수료(수납액). 승인금액(받기로 된 금액)은 기록용이며 어떤 매출 합산에도 들어가지 않는다.
> - **누가 읽나요**: 개발자, 에이전트
> - **어떤 기능·작업과 연결?**: 대시보드 KPI(loadDashboard), 전광판 매출 랭킹(scoreboard), 시트 수수료총합(01!O5)·수납총액(02!D3), splitContractRevenue/computeContractRevenue
> - **읽고 나면 알 수 있는 것**: (1) 승인 vs 수납 정의 (2) 매출 SSOT (3) 시트·코드 어디에도 승인이 섞이면 안 되는 이유
> - **관련 문서**: docs/domains/data-model.md(DashboardKPI), 인시던트 2026-06-12-carryover-revenue-leak, [[reference-vat-principle]]

- **status**: accepted
- **date**: 2026-06-23

## 맥락
02 계약수납관리의 각 수납 슬롯에는 **승인금액**(기관이 승인한, 받기로 된 금액)과 **수납액**(실제 입금된 수수료)이
따로 있다. 매출은 "실제 받은 돈"이어야 하는데, ① 전광판 개인 매출 랭킹이 대시보드 총매출 셀(승인 포함 가능)을
읽었고, ② 일부 시트 템플릿의 수수료총합/총매출 수식이 02!D2(승인총액)+D3(수납총액)을 합산해 매출이 부풀려졌다.

## 결정
1. **매출 = Σ수임료 + Σ수납액.** 승인금액은 **기록용**이며 매출·영업이익·전광판 어디에도 합산되지 않는다.
   - 이월(구분="이월" OR 계약일<시작일)은 아레나 매출에서 제외(arena-start-revenue-split, 불변).
   - SSOT = `lib/service/dashboard.ts`의 `computeContractRevenue`/`splitContractRevenue` (수납액만 합산, 승인 미참조).
2. **모든 매출 경로가 이 정의를 공유한다.**
   - 대시보드 KPI(loadDashboard): 이미 정상(JS 서버 합산).
   - 전광판 개인 매출 랭킹: 시트 총매출 셀 의존 제거 → `splitContractRevenue(...).arena.revenue` 로 계산(KPI 와 동일).
   - 시트 수수료총합 `01 영업관리!O5 = '02 계약수납관리'!D3`(이월제외 수납총액)만 — 승인총액 D2 미포함.
3. **02!D2(승인총액)는 기록용 셀로 유지** — 매출 합산식에서 빠지기만 하면 된다.

## 근거
- "받기로 된 돈"과 "실제 받은 돈"은 다르다. 매출/순위/이익은 실수령 기준이어야 공정·정확.
- 코드(JS)와 시트(수식) 두 경로가 같은 정의를 쓰지 않으면 화면마다 매출이 어긋난다.

## 영향
- 전광판 매출 랭킹 값 = 그 사람 대시보드 KPI 총매출(splitContractRevenue.arena.revenue)과 항상 일치.
- 시트 직접 열람 수수료총합(O5)도 수납만 반영 — admin 의 setup-formulas 재실행 시 §2.5 가드로 멱등 설치(raw 보존).
- 대시보드 탭 셀(B21:G21/D21)은 구조테스트상 코드 쓰기 금지 — 앱 표시는 JS 로 정상이라 화면 영향 없음. 시트 raw 셀이 D2 를 직접 참조하면 별도 교정 필요(후속).

## 후속
- 결정 변경 시 새 ADR 로 supersede. 매출에 승인을 섞으려는 변경은 이 ADR 위반.
