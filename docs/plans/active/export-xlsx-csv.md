## 0. Relation 정정 (2026-08-10) — BBE-71 은 BBE-68 과 무관하다

**이전 판단(§0 구판, 2026-08-09)이 틀렸다.** R7 로드맵 Phase 4 표의 "선행" 칸만 보고 "BBE-71
선행 = #19(BBE-68)"라고 적었는데, **정본은 ADR**이고 ADR-0030 을 직접 재확인한 결과 그 관계는
존재하지 않는다.

**ADR-0030 §2·§3 원문 그대로**: 시트 자동 미러 폐지(R7-#20, **BBE-69**)는 아래 3개 조건을
**전부** 요구한다 — ①R7-#18(BBE-67) 완료 ②R7-#19(BBE-68) 완료 ③R7-#22(**BBE-71**) 완료.
즉 **68 과 71 은 둘 다 69 를 막는 독립된 선행조건**이지, 68 이 71 을 막는 게 아니다. §3 은 이걸
더 명확히 한다: "export(BBE-71)가 실제로 동작하기 전에는 미러(BBE-69)를 끄지 않는다... **Linear
에는 이미 BBE-69 blocked_by BBE-71 로 배선돼 있다**." — 배선 대상은 **69→71** 이지 71→68 이
아니다.

**belie 지적(2026-08-10) 그대로**: "ADR 순서구속은 71 → 69(Export 가 미러 폐기보다 먼저)이고,
68 과는 무관하다." → **BBE-71 은 R7 Phase 1(레지스트리 DB화)·BBE-68(게이트 제거)을 기다릴
필요 없이 지금 착수 가능.** 오히려 "신규 제작이라 리드타임이 길다 — 지금 시작해야 69 에서 안
막힌다"(belie) — 착수를 미룰수록 69 의 착수 가능 시점이 뒤로 밀린다.

**카드 relation 수정 요청(Linear, 이 세션 미인증이라 직접 수정 불가 — 반장 대행 필요)**:
`BBE-71 blocked_by BBE-68`(있다면) **삭제**. `BBE-69 blocked_by BBE-71`은 **그대로 유지**(ADR
이 명시한 정본 관계). 근거는 위 ADR-0030 §2·§3 인용 그대로.

**파생 효과 — §2.2 "데이터 소스" 재검토 필요**: 구판은 "이 카드가 Phase 4 이후 착수되니 전
기수가 DB 정본일 것"을 전제로 "DB 우선, 시트 폴백 없음"을 권장했다. **그 전제가 깨졌다** — 지금
착수 시점엔 파일럿 4개 기수만 DB 정본이고 나머지는 시트가 유일한 정본이다. DB-only 로 만들면
비파일럿 학생은 **export 가 조용히 텅 빈 파일**이 된다(이번 세션 내내 봐온 실패 패턴과 동일 —
BBE-64 A2 백필 사례 등). §2.2 를 시트-읽기 기반으로 다시 썼다 — 아래 참고.

## 1. 미결 3가지 (R7 §G.1) — 권장안

### ① 형식 — xlsx 단일로 시작, csv 는 보류(YAGNI)
카드 제목이 "xlsx/csv" 둘 다 언급하지만, 실사용 맥락(학생이 잃는 것 = **여러 탭짜리 구글시트**)을
보면 xlsx(다중 시트 워크북)가 지금 경험과 1:1 대응이라 더 낫다. csv 는 탭 하나만 담을 수 있어
"내 기록 전체"를 표현 못 한다(탭마다 파일이 여러 개로 쪼개짐). **CLAUDE.md YAGNI 원칙**("언젠가
쓸 수도 있어서" 금지) 대로, 구체적 필요(예: 다른 프로그램에 기계적으로 재수입)가 실제로 나오기
전까지는 xlsx 하나만 만든다. csv 는 후속 카드로 미룬다.
- **belie 결정 필요 여부**: 낮음(권장안 채택 시 질문 불요) — 반대 의견 있으면 알려달라.

### ② 범위 — 개인 전체 스냅샷(현재 탭 구조를 시트별로 그대로)
"시트는 다운로드 버튼 형태로 남긴다"(belie 08-05 확정)의 취지 = 오늘 시트가 담고 있는 걸
그대로 파일로 가져갈 수 있으면 된다. 그러므로 MVP 범위 = **로그인한 사용자 1명의 데이터 전체**를
현재 탭 구조 그대로 시트 여러 개(워크시트)로 묶는다:
| 워크북 시트 | 소스(오늘 기준) | 비고 |
|---|---|---|
| 업체관리(04) | `readAllMeetings` | 미팅 전체 |
| 계약수납(02) | `contract-payment.readAll` | 계약 전체(BBE-53 자연키 upsert 이후 안전) |
| DB관리(03) | `readPurchases/readProductions/readBanners/readLeads` | 4섹션 |
| ~~영업관리~~ | ~~재계산~~ | **MVP 스코프 밖(§4, 2026-08-10)** — 후속 카드 |
| ~~대시보드 요약~~ | ~~`dashboard-aggregates.ts`~~ | **MVP 스코프 밖(§4, 2026-08-10)** — 후속 카드 |

**belie 결정 필요**: **범위를 "학생 개인 전체"로 한정**하는 것에 동의하는지. (기수 전체 admin
일괄 export 는 다른 유스케이스라 별도 카드 권장 — 아래 ③ 참조)

### ③ 사용 주체 — 학생 self-service 우선, admin 대량은 후속
로그인한 학생이 "내 기록 내려받기" 버튼으로 자기 데이터만 받는 것이 1순위(시트 대체 목적에
정확히 부합). admin/트레이너/회장의 **여러 학생 일괄** export 는 스코프가 다르다(권한 검사·
대용량 처리·zip 묶음 등 추가 설계 필요) — 이 카드에서 안 하고 후속 카드로 분리 제안.
- **belie 결정 필요**: 위 우선순위(학생 우선, admin 일괄은 후속 카드)에 동의하는지.

## 2. 기술 설계 초안

### 레이어 (CLAUDE.md §2 단방향 원칙 준수)
```
lib/service/export-xlsx.ts   — 순수 조립: 각 도메인 서비스 함수를 호출해 워크북 데이터 구조로 변환
                                (다른 service 함수를 호출하는 것은 기존 관행, contract-payment-add.ts 참고)
app/api/export/route.ts      — Route Handler: 인증(본인 이메일만) → service 호출 → xlsx 버퍼 반환
                                Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
                                Content-Disposition: attachment; filename="내기록_{날짜}.xlsx"
components/                  — "내 기록 다운로드" 버튼(설정 화면 후보) — 클릭 시 위 라우트로 이동/fetch
```
`googleapis` 는 이 경로 어디에도 안 들어간다(§2 규칙2 저촉 없음) — xlsx 생성은 Sheets I/O 가
아니라 순수 데이터 직렬화다.

### 라이브러리 후보
현재 xlsx/csv 의존성 0(R7 §D 확정). 후보 2개:
| 후보 | 장점 | 단점 |
|---|---|---|
| **`xlsx`(SheetJS CE)** | 가볍다(VPS 빌드 메모리 제약 — `NODE_OPTIONS=--max-old-space-size=2048`
  참고), 멀티시트 쓰기 무료(CE)로 충분, API 단순 | 셀 스타일링 제한적(지금 요구사항엔 불필요) |
| `exceljs` | 서식·freeze pane 등 풍부 | 더 무겁다, 지금 필요 없는 기능 |

**권장 = `xlsx`(SheetJS)**. 지금 요구(데이터 그대로 옮기기)에 서식 기능이 불필요하고, "Tools
적을수록 좋다"(CLAUDE.md §0) 원칙과도 맞는다. 서식 요구가 나중에 생기면 그때 재검토.

### 데이터 소스 — 시트 읽기 기반(2026-08-10 정정, §0 참고)
구판은 "DB 우선"을 권장했으나 그 전제(전 기수 DB 정본)가 착수 시점 기준 거짓이다. **기존
repo 함수를 그대로 재사용**한다 — 새 읽기 로직을 안 만든다(레이어 규칙 §2 준수, 중복 회피):
- `readAllMeetings(sid)`(`lib/repo/meetings.ts`) — 04 업체관리
- `readAll(sid)`(`lib/repo/contract-payment.ts`) — 02 계약수납
- `readPurchases/readProductions/readBanners/readLeads(sid)`(`lib/repo/db.ts`) — 03 DB관리 4채널

이 함수들은 파일럿·비파일럿 구분 없이 항상 시트에서 읽는다(R2/R3 가 손댄 건 **쓰기**·일부
**개인 화면 읽기**뿐, 이 repo 함수 자체는 무변경) — 그래서 export 는 **오늘 기준 모든 사용자**에게
동일하게 동작한다. R7 Phase 2 가 진행돼 이 함수들이 DB-aware 로 바뀌면(예: `chooseDailySource`
같은 게이트가 이 경로에도 생기면) export 는 자동으로 그 변경을 상속한다 — 이 카드가 별도 게이트를
만들 필요 없음.

## 4. 남은 위험 / 후속 결정 필요

- **전광판 주차별 5지표(C33:H40) = DB 경로가 아직 없다**(R7 §C 확정) — 이 카드가 그 경로를
  처음 만들게 될 수도 있다. **자율 결정(§0.7, 2026-08-10)**: MVP 범위에서 뺀다. "영업관리

  계약수납·DB관리)만. 되돌리기 쉬움(추가 워크시트를 나중에 얹는 것뿐, 기존 3개 무변경).
