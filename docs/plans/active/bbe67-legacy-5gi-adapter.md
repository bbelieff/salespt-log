## 0. 배경 — 이 세션이 인수한 경위

Linear BBE-67 코멘트 전체 실측(§0.8 Gather):
1. G작업원D 가 5기 manifest(source 8개 확정) + 예상 행수(sales 515·contracts 37·db 38·합계 590)
   를 산출했으나 **aggregate-only**(실제 grid parsing 검증 없음)였다.
2. 반장이 C작업원B 에게 어댑터 lease 발급 — "탭 이름만 맞추지 말고 §4(행수는 맞는데 데이터가
   틀리는 경우) 를 경계하라"는 명시 경고 포함.
3. C작업원B 가 착수 직후 §0.8 Gather 를 따라 먼저 구조를 확인 → **sales·db 구조가 현행 파싱
   가정과 다르다는 것을 실측 확정** → 근거 없이 코드를 짜는 게 더 위험하다고 판단해 **코드 0줄로
   STOP**, "정밀 census 먼저"를 제안(Linear `36bedd6d`).
4. belie 직접 지시로 이 세션이 인수 — "census 먼저, 그다음 어댑터. 590 dry-run 은 어댑터 완료
   후에만"(G작업원D 코멘트 `81bb70c7`③ 과 동일 게이트).

**이 문서는 그 정밀 census 를 실행한 결과다.** C작업원B 의 STOP 판단은 옳았다 — 아래 §2 가 보여주듯
sales·db 둘 다 실제로 현행 가정과 구조적으로 다르다.

  옮기지 않았다**(격리 확인). 이후 모든 조회를 헤더/라벨 전용 range 로 좁혀 재발 방지.
- **표본**: 전체 8/8 sentinel(헤더 존재 확인) + 대표 2개(source-1·source-5, 예상행수 74·61로

## 2. Census 결과 — 현행 vs 5기 legacy

### ✅ meetings·todos·company_archive — 변경 불필요(C작업원B 판정 재확인)
5기 8/8 시트 모두 정확히 6탭: 대시보드·DB관리·영업관리·계약관리·DB관리(예시)·영업관리(예시).
`04 업체관리`·`05 실무투두`·`06 업체정보` 탭 자체가 **존재하지 않는다**(다른 이름 아님, 완전 부재
— C작업원B §3(B) 판정 재확인·확정). 현행 `backfill-sheet-rows.mjs` 는 이미 "탭 없음=영구·무해"로
정확히 분류한다. **코드 변경 0.**

### ⚠️ sales(영업관리) — 구조 다름, 그러나 핵심 지표 컬럼은 우연히 동일

| 항목 | 현행(7기+) | 5기 legacy | 판정 |
|---|---|---|---|
| 탭 이름 | `01 영업관리` | `영업관리`(번호 없음) | alias 추가 필요 |
| 시작일 앵커 | O1 셀(고정) | **없음** — 각 행에 날짜 직접 기록(C열) | 앵커 불필요, 더 견고 |
| 주차 stride | 34행/주(코드 상수) | **34행/주 — 실측 확인, 동일** | 변경 불필요 |
| 요일당 채널행 | 4행(포지션으로 채널 결정) | **4행, 동일 포지션 규칙** | 변경 불필요 |
| 날짜 컬럼 | (앵커+오프셋 계산) | **C열 직접 기록**(요일당 블록 첫 행) | 계산 대신 직접 읽기 — 더 정확 |
| 채널 라벨 1-3 | (라벨 없음, 포지션만) | "매입DB"/"직접생산"/"현수막" 명시 기록(D열) | 위치 규칙 교차검증 가능(§3) |
| **채널 라벨 4** | `콜·지·기·소`(4종 통합) | **`지-기-소`(3종만, "콜" 없음)** | ⚠️ **belie/반장 결정 필요**(§5) |
| 지표 컬럼(E~H) | 생산/유입/컨택진행/컨택성공 | **E~H 헤더가 동일 순서로 확인**(생산건수▶·유입건수▶·컨택진행수▶·컨택성공건수▶) | **컬럼 위치 동일 — 변경 불필요** |
| 헤더행 | (코드에 없음, 순수 좌표) | r8-r9(주차마다 반복) — I~R 에 미팅·계약·실적 관리 필드 있으나 **현재 DB 스키마엔 대응 필드 없음** | I~R 은 스코프 밖(§4) |
| 시트 총 높이 | 349행(10주 예약) | source-1·5 공통 **277행 실사용**(약 8주분) | 넉넉한 범위(10:400)로 읽고 빈 행 skip — 변경 불필요 |

**결론**: C작업원B 의 "구조가 다르다" 판정은 정확하다(앵커 없음·라벨 방식·헤더 다름). 그러나
**정작 코드가 실제로 읽는 4개 지표 컬럼(E~H)의 의미와 위치는 우연히 동일**하다 — 이것이 "행수는
맞는데 데이터가 틀리는" 최악의 시나리오를 피하게 해준다. 어댑터는 날짜 원천만 O1-앵커 계산에서
C열 직접 읽기로 바꾸면 되고, 나머지(주차 stride·채널 포지션·지표 컬럼)는 현행 그대로 재사용
가능하다.

### ⚠️ db(DB관리) — 4섹션 배치가 완전히 다름(2x2 혼합, 현행은 4열 병렬)

| 섹션 | 현행(7기+) 컬럼 | 5기 legacy 컬럼·행 |
|---|---|---|
| 매입DB | B:H (rows 4:100) | **B:G**(rows 4:~9, r10=합계) |
| 직접생산 | I:O (같은 행 범위, 옆으로) | **K:P**(같은 행 범위 — 매입DB 와 나란히는 맞으나 컬럼 시작이 다름) |
| 현수막 | P:V (같은 행 범위) | **B:H, rows 14:~19**(r20=합계) — **매입DB 아래로 쌓임**, 옆이 아님 |
| 콜지기소 | X:AD (같은 행 범위) | **B:H, rows 24:~?**("지인, 기고객, 소개" 통합 1섹션) — 현수막 아래로 더 쌓임 |

**결론**: 현행은 4섹션이 전부 같은 행 범위에서 옆으로(B~AD) 나란히 배치되지만, 5기는
[매입DB|직접생산]이 나란히 배치된 뒤 **그 아래로 현수막, 다시 그 아래로 지인/기고객/소개**가
쌓이는 2단 배치다. 헤더 텍스트 확인(안전, PII 아님):
- 매입DB(B4:G4): 구매일·업체명·개당단가·주문개수·주문금액·기타
- 직접생산(K4:P4): 날짜·소재·기간예산·생산개수·개당단가·기타
- 현수막(B14:H14): 날짜·업체명·(미상 1열)·개당단가·주문개수·(미상 2열)
- 지인기고객소개(B24:H24): 구분·접수일·대표자명·업체명·소개처·연락처·조건

각 섹션은 "합계"(총계) 행으로 끝난다 — 데이터 종료 판정에 "합계" 라벨 감지를 사용한다(수기
행수가 학생마다 다르므로 고정 행수 가정 대신).

### ✅ contracts(계약관리) — G작업원D 서술 검증 완료(C작업원B 미검증 상태였던 것)

- 탭 이름: `계약관리`(번호 없음, 현행 `02 계약수납관리`/`02 계약관리` 와 다름 — TAB_ALIASES 에
  이미 있는 alias-list 패턴에 항목만 추가하면 됨)
- **row10 = 헤더**("계약일"·"업체명"·"수임비"·...), **row11 = 예시행**(단일문자 placeholder
  값들 — 실측: F/G/H 열이 전부 1자리 텍스트, 실제 계약 데이터로 보기엔 값 형태가 부자연스러움),
  **row12+ = 실데이터**(다자리 숫자 확인) — **G작업원D 의 서술이 실측으로 확정됐다**(C작업원B
  보고서가 "여전히 검증되지 않음"이라 남겨둔 부분).
- 계약일 컬럼 = C열(현행과 동일 가정) — census 로 재확인.

## 3. 어댑터 설계

파일: `scripts/ops/backfill-sheet-rows.mjs`(반장 lease 대상 그대로, `lib/**`·`app/**` 무접촉) +
신규 `scripts/ops/backfill-sheet-rows-legacy.mjs`(순수 상수·계산만, googleapis 의존 0 —
단위테스트를 위해 분리, lease 가 명시 허용한 "어댑터 단위 테스트"의 전제 조건이었다: 원본
스크립트는 최상위에서 `--cohort` 없으면 `process.exit(1)` 하므로 import 만으로 테스트가 죽는다
— `isMainModule` 가드로 CLI 전용 코드만 감싸 해결, 현행 실행 경로는 100% 동일).

- **contracts**: `TAB_ALIASES`류 리스트에 `["계약관리", 12]` 추가(기존 `["02 계약수납관리",6]`·
  `["02 계약관리",5]` 옆). 추출 로직 변경 없음(계약일=C열 가정 그대로 유효).
- **db**: 탭 이름에 `"DB관리"`(무접두) 추가. 섹션 정의를 **고정 좌표 4개**에서 **섹션별
  (라벨탐지 또는 명시좌표) + "합계" 종료 감지**로 일반화. 5기 전용 섹션 좌표(매입DB B:G·
  직접생산 K:P·현수막 B:H@r14·지인기고객소개 B:H@r24)를 별도 legacy 프로필로 등록 —
  **현행 시트의 섹션 좌표는 100% 그대로 유지**(회귀 위험 0, legacy 프로필은 탭 이름
  "DB관리"(무접두)로만 트리거).
- **sales**: 탭 이름에 `"영업관리"`(무접두) 추가. **O1 앵커 읽기를 조건부로 건너뛰고, 각
  요일 블록의 C열(날짜)을 직접 읽어 사용**하도록 분기. 주차 stride(34)·채널 포지션(4행)·
  지표 컬럼(E~H)은 **완전히 재사용**(위 §2 표에서 확인된 동일성 근거). 채널 4번째 라벨은
  §5 belie 결정 전까지 **legacy 원문("지-기-소") 그대로 저장** — 현행 라벨로 임의 변환하지
  않는다(없는 데이터를 지어내지 않는다).
- **meetings·todos·company_archive**: 코드 변경 없음(§2 확인).

## 4. 스코프 밖(사용 안 함, 명시)

- sales I~R 열(미팅 상세·계약 요약·실적) — 현재 `sheet_rows` sales payload 스키마에 대응 필드가
  없다. 새 필드를 만드는 건 이 카드 범위 밖(BBE-134 파일럿 meetings 갭과는 무관한 별개 확장) —
  **읽지 않는다**, 억지로 끼워 넣지 않는다.
- BBE-134(파일럿 meetings 부분백필 갭) — 이 카드가 아니다(별도 소유).
- 실제 `--execute` — 이 PR 은 **dry-run 까지만**. 실행은 BBE-67 소유(G작업원D)의 별도 계약.

## 5. belie/반장 결정 필요 — sales 4번째 채널 라벨

5기 legacy 는 "지-기-소"(지인·기존고객·소개 3종 통합)만 있고 "콜"(콜드콜) 카테고리가 없다.
현행 채널은 "콜·지·기·소"(4종). 세 가지 선택지:

① **원문 그대로 저장**("지-기-소" 별도 라벨) — 역사적 정확성 유지, 그러나 현행 채널 4색
   집계·대시보드가 이 라벨을 모르는 값으로 처리(집계 누락 가능성).
② **`콜·지·기·소` 로 매핑**(값은 지인+기존+소개 합계로 간주) — 현행 집계와 호환되지만
   "콜 실적이 0"이라는 잘못된 신호를 만들 수 있음(실제로는 "콜이라는 개념 자체가 없었다"와
   "콜을 했는데 0건이었다"는 다른 의미).
③ **둘 다** — 원문 라벨은 보존하되 표시 레이어에서 "콜·지·기·소"로 합산 표시.

**권장**: ①(원문 보존) — 이유: 시트 은퇴(BBE-69) 후 sheet_rows 가 유일한 정본이 되므로, 지금
데이터를 지어내면 되돌릴 수 없다. 집계 누락은 나중에 표시 레이어에서 고칠 수 있지만, 원문을
지금 뭉개면 그 정보는 영원히 사라진다(비가역성 비교 — ADR-0030 §2 사고방식과 일치).
**이 PR 은 권장안(①)으로 dry-run 을 실행한다** — belie/반장이 다른 안을 원하면 execute 전에
