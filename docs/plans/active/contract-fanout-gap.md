# 계약 팬아웃 유실 (2026-09-01)

## 증상

belie 신고 — **"문병규 계약이 4건으로 나오는데 실무수납에는 3건만 뜬다. 수강생도 이상해서 연락왔다."**

## 실측

10기 문병규 님 시트 원본 대조:

| 탭 | 케이탑전기진단 |
|---|---|
| `04 업체관리(앱자동작성용)` 283행 | **있음** — 2026-08-31 15:00, 매입DB, 상태 **계약**, **₩1,100,000** |
| `02 계약수납관리` 179~181행 | **없음** — 제일수도사·전남석재·밥한잔 3행뿐 |

`/payment` 총매출 ₩190,000 = 40,000+100,000+50,000 (3행 합)과 정확히 일치.
일정·계약 탭은 같은 주 매출을 ₩1,150,000 으로 표시. **110만원이 장부에서 빠졌다.**

시트·DB 양쪽에 똑같이 없으므로 미러 드리프트가 아니다 —
기존 `db-contract-drift-audit.mjs`(02 의 시트↔DB 비교)로는 못 잡는 유형이다.

## 근인 — 두 번의 쓰기, 맞춰주는 사람 없음

```
① 04 미팅에 상태=계약 기록   (patchMeeting)        ← 대시보드 「계약 4건」이 세는 것
② 02 계약수납에 행 append    (addContractPayment)  ← 실무/수납 「3건」이 세는 것
```

`app/(app)/schedule/page.tsx` 의 옛 코드에 구멍이 둘 있었다:

- **ⓐ 조용한 성공** — ② 직전에 `weekQuery` 를 **다시 뒤져** 미팅을 찾았다. 아직 갱신 전이거나
  주차가 바뀌어 못 찾으면 **`✓ 저장 완료 (meeting lookup 실패 — fan-out 생략)`** 라는
  **성공 표시**를 띄우고 ②를 통째로 건너뛰었다. 수강생은 초록 체크를 보고 넘어간다.
- **ⓑ 복구 불가** — ②는 `!wasAlreadyContract` 일 때만 돌았다. 한 번 빠지면 카드는 이미
  「계약」이라, 다시 저장해도 ②가 영영 안 돈다.

## 해결

**판정을 순수함수로 분리** — `app/(app)/schedule/_lib/contract-fanout.ts:decideContractFanout`

| | 전 | 후 |
|---|---|---|
| 출처 미팅 | patch **후** 재조회 | patch **전** 값 하나만 사용(재조회 제거) |
| 못 찾았을 때 | `✓ 저장 완료` (조용히 생략) | **blocked** — 무엇을 해야 하는지 알린다 |
| 이미 계약인 카드 | ② 안 돎 | **② 돎** → 재저장이 곧 복구 |
| ② 실패 | 경고 1회, 끝 | **자동 1회 재시도** 후 안내 |

재실행이 안전한 근거: `appendFromContract(dateCompanyFallback=true)` 는 연결 미팅 id →
(계약일+업체명) 순으로 기존 행을 먼저 찾아 **그 행을 갱신**한다(BBE-53, `lib/repo/contract-payment.ts:217`).
새 행을 만들지 않으므로 매출 이중계상(#558)이 나지 않는다.

## 전수 감사

`scripts/ops/contract-fanout-gap-audit.mjs` (읽기 전용) — 수강생 1명당 batchGet 1회,
`04` 의 상태=계약 도장과 `02` 행을 **앱과 같은 규칙**(AK 연결 미팅 id → 계약일+업체명)으로
짝지어 누락을 센다. 누락 건의 업체명·날짜·금액과 **합계 금액**을 출력한다.
워크플로 `Contract Fanout Gap Audit (read-only)` 로 VPS 원격 실행.

## 남은 일

1. 감사 실행 → 영향 범위 확정 → 누락 건 복구(수강생이 해당 카드를 다시 계약으로 저장하면 채워진다).
2. **서버측 팬아웃 검토** — 지금은 여전히 클라이언트가 두 번 호출한다. 탭을 닫거나 네트워크가
   끊기는 창은 남아 있다. ①을 처리하는 API 가 ②까지 한 요청에서 끝내면 그 창이 사라진다.
3. 감사를 주기 실행(cron)해 다음 유실을 사람이 아니라 도구가 먼저 발견하게.
