# DB-정본 & 무제한 CRM 로드맵 (2026-07-07 사용자 결정)

## 0. 왜 (전략 배경 — 재논의 금지)
- 기존: 시트가 8주 구조라 수료=사용 종료 → **락인 소멸**. 아레나로 수료생이 대거 복귀한 지금,
  끊으면 "모두가 경영일지를 쓰는 큰 그림"이 무너짐 → **수료 후에도 CRM 계속 제공**.
- 물리 전제: 01 영업관리 시트가 8주×34행 고정 → 무제한은 **DB 정본 전환 후에만** 가능.
- 속도 KPI: DB 전환의 제1 목적은 여전히 속도(#484 계측 기준선 대비 개선을 매 단계 실증).
- 단계 정의(수파베이스 세션과 공유): **1단계 = 앱→구글시트→DB**(이중 기록) /
  **2단계 = 앱→DB→시트**(DB 정본, 시트=미러/export).

## R0. 파일럿 완주 — 1단계 확립 (진행 중, ~7/10)
- ✅ 인프라(#485)·연결 실증(keep-alive·admin OK) / 🔄 feat/db-dual-write + 8기 backfill(프롬프트 4)
- 9기 생성(7/10 시작) → 첫날부터 이중 기록. 정합 대조(admin 진단) 며칠 관찰.
- 산출: 시트↔DB 행수 일치 리포트. **성공 판정 시 R2 진입.**

## R1. 구글 캘린더 연동 (준비 100% — R0 프롬프트 4 머지 후 끼워넣기 가능)
- feat/gcal-connect → feat/gcal-sync-engine (SoR: google-calendar-sync.md). DB 트랙과 독립 기능이지만
  레포 구역 겹침 → 순차 머지. 출시 시 NEW 뱃지 자동(calendar.gcalCard).

## R2. 읽기 전환 — "빨라졌다"를 실증 (2단계 전반부)
- 탭별 read 를 시트→DB 로 교체(컨택 → 일정/계약 → 실무/수납 → DB생산 → 캘린더).
  PR 단위 = 탭 1개씩, 각 PR 수용 기준에 **#484 대비 응답시간 개선 수치** 포함.
- 대시보드 = 시트 수식 재현을 **SQL 집계로 재구현** + 수식 값과 자동 대조 테스트(전환 기간 병행).
- 산출: p50/p95 전후 비교표. jsonb 미러 → 필요 지점부터 정규화 컬럼 추출(YAGNI 순서).

## R3. 쓰기 정본 전환 — 앱→DB→시트 (2단계 완성)
- 쓰기 경로 뒤집기: DB 가 정본, 시트는 **후행 미러**(fire-and-forget export, 운영자/트레이너
  열람용) — 시트 미러 유지 여부는 D3 결정에 따름.
- 기수 생성 = DB insert(시트 생성 옵션화) → "매 기수 시트 생성 귀찮음" 소멸.
- §2.5 보존 가드·수식 재설치 계열 운영 부담 대거 은퇴. 잠금/충돌은 DB 트랜잭션으로.

## R4. 8주 제한 해제 — 무제한 CRM (R3 이후에만 가능)
- **ADR 신규(0005 supersede)**: 수강 8주 = "코스 기간"(통계·아레나 집계 기준)으로 의미 축소,
  사용 자체는 무제한. 편집기간 가드(+69일 읽기전용) 제거/재정의.
- 주차 모델: DB 에선 주차 무제한(수강시작 기준 연속 주차). 대시보드에 "수강 기간(1~8주) vs
  이후" 구분 표시. 기존 8주 하드코딩 지점 전수 제거(구조 테스트로 가드).
- 수료생 온보딩: 종강 후에도 로그인 유지(archived 라우팅 규칙 개정 — 현재는 클레임 유도용).

## R5. 아레나 마이그레이션 + 기수 체계 통합
- 아레나 37+ 시트 데이터 DB 적재(backfill 재사용).
- **라벨 통합: A1-N기 → N기** — 레지스트리·클레임·전광판·audience(A 접두 판정) 로직 전면 개정.
  ⚠️ 충돌 설계 필수: 기존 N기(archived) 행과 A1-N기 행의 병합 규칙(같은 사람 = 이력 통합,
  이월 깃발은 DB 플래그로 계승). 전광판 "아레나" 개념은 기간 이벤트로 재정의.
- R4·R5 는 상호 의존(수료생 지속 사용 ↔ 아레나 상시화) — 상세 설계는 R2 완료 후 별도 plan.

## B. 유료 전환 준비 (Billing-ready — 2026-07-07 사용자 확정)
> 방침: 당분간 무료로 락인 확대 → **충성유저 50~100명 + 앱 고도화·안정화 시점에 결제 부착.**
> 지금 결제를 만들지 않되, 붙이는 날 "스위치만 켜면" 되도록 구조를 선행 준비한다.
- **B1 (R2~R3 에 포함)** 스키마 자리: users 에 `plan`(기본 free) · `plan_expires` · 확장 여지.
  전원 free 로 시작 — 코드 동작 무변화.
- **B2 (R3 에 포함)** 권한 게이트 단일화: "이 기능 사용 가능?" 판정을 단일 entitlement 함수로
  통일(코드 곳곳에 흩뿌리지 않기 — 결제 도입 = 이 함수 하나 수정). 지금은 항상 허용.
- **B3 (R4 와 함께)** 전환 판단 계기판: admin 에 "수료 후 활성 사용자 수 · 주간 활성 ·
  8주 이후 잔존율" 카운터(PostHog 기반) — 50~100명 도달을 숫자로 확인.
- **B4 (결제 착수 시점)** PG 조사·연동(토스페이먼츠/포트원 등 국내 정기결제), 약관·환불규정,
  플랜/가격 실험. 별도 plan 문서로 그때 기획.
