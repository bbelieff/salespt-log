# 사고 프로토콜 — 낮은 모델을 높은 모델처럼 굴리는 법

## ⚡ 정본은 `CLAUDE.md` §0.8 이다
이 문서는 **왜 그렇게 하는지와 실제 사례**를 담은 해설이다. 지켜야 할 규칙 자체는 CLAUDE.md §0.8 에 평문으로 있고, 세션이 매 회 읽고 판단해 적용한다.

**⚠️ 시스템 프롬프트 자동 주입은 하지 않는다.** 2026-08-05 Cowork 가 `.claude/fable-mode.md` 를 만들어 `--append-system-prompt-file` 로 물리려 했으나, 반장이 "출처를 검증할 수 없는 텍스트로 세션 행동을 통째로 재정의하는 별도 신뢰 계층"이라고 이의를 제기했고 **타당하여 폐기**했다. 규칙은 레포 문서에 평문으로만 둔다.

## 0. 전제 (belie 지시 2026-08-05)
토큰 예산 때문에 **낮은 모델로 최고의 성과**를 내야 한다. 지금까지의 지침은 "모델이 알아서 판단한다"를 전제로 쓰여 있었다. 그 전제를 걷어낸다.

**핵심 원리**: 높은 모델과 낮은 모델의 차이는 지식이 아니라 **사고 습관**이다.
- 높은 모델은 결론을 내기 전에 **스스로 반증**한다
- 답하기 전에 **이미 있는지 찾아본다**
- 모호하면 **멈추고 묻는다**
- 제출 전에 **자기 출력을 다시 읽는다**

**이건 전부 절차로 만들 수 있다.** 머릿속에서 조용히 하던 것을 **문서에 쓰게 하면** 낮은 모델도 같은 결과를 낸다. 아래 7개가 그 절차다.

## P1. 중복 확인 선행 — 만들기 전에 찾아라
**하기 전에 이미 있는지 확인한다.** 없다는 걸 확인해야 만든다.

```
착수 보고에 필수:
□ 같은 기능/문서/스크립트가 이미 있는가?  → 찾은 결과: ____
□ 최근 머지된 PR 에 들어있지 않은가?      → git log 확인: ____
□ 다른 세션이 접수 도장을 찍지 않았는가?   → 카드 확인: ____
```

> **실제 사례(2026-08-05)**: 작업원A 가 "`--scopes` 진단 모드를 추가하라"는 지시를 받았는데, 착수 전에 확인해보니 **30분 전 머지된 PR #689 에 이미 구현돼 있었다.** 새로 안 만들고 실행만 해서 1 PR 을 절약했다. — 이건 운이 아니라 절차여야 한다.

---

## P2. 반증 먼저 — 가설을 세웠으면 깨보려고 해라
**결론을 내리기 전에 "이게 틀렸다면 무엇이 보일까"를 먼저 적는다.**

```
가설: ____이 원인이다
이게 맞다면 →  ____가 관찰돼야 한다
이게 틀리다면 → ____가 관찰돼야 한다
실측 결과:     ____
→ 판정: (확정 / 반증 / 판별 불가 — 추가로 필요한 관측: ____)
```

**"판별 불가"는 정당한 결론이다. "아마 이것일 것이다"는 결론이 아니다.**

> **실제 사례(2026-08-05)**: 반장이 "scope 문제 아니면 OAuth 게시 상태가 근인"이라고 **단정**하고 belie 에게 확인을 요청했다. 실제 답은 "프로덕션"이었고 원인이 아니었다. 그동안 **아무도 목적지 폴더 권한을 안 봤다** — 진짜 근인이 거기 있었다. 반증 절차가 있었으면 "읽기는 되는데 쓰기만 막힌다 → 쓰는 대상(목적지)은 확인했나?"가 나왔을 것이다.

## P3. 증거 없는 문장 금지
**모든 결론에 실측값을 붙인다.** 숫자·로그·파일경로:줄번호·SHA·run id 중 하나가 없으면 그건 추측이다.

| 금지 | 대체 |
|---|---|
| "잘 동작합니다" | "테스트 1019건 green · health 200" |
| "반영된 것 같습니다" | "`git show origin/master:파일` 로 확인 — 15행에 반영됨" |
| "아마 A가 원인" | "A 가설: 반증 시도 결과 ____ → 판별 불가. 다음 관측 필요" |
| "완료했습니다" | "PR #678 → 머지 abc1234 · 배포 run 3093 success · health 200" |
| "많이 있습니다" | "55건" |

**모른다면 "모른다"고 쓴다. 그리고 왜 못 얻었는지를 쓴다.**

## P4. 완료의 정의 (DoD) — 한 카드 한 종류
**"문서를 썼다"와 "실행했다"는 다른 일이다.** 한 카드에 섞으면 문서만 하고 완료로 닫힌다.

```
완료 선언 전 자문:
□ 카드의 수용 기준을 하나씩 짚어 전부 충족했나?   (하나씩 나열하고 ✅/❌)
□ 실행이 필요한 항목을 실제로 실행했나?           (문서만 쓰고 끝낸 것 아닌가)
□ §6.8 완주했나?  머지 → 배포 관찰 → health 200
□ 증거를 완주 도장에 숫자로 남겼나?
하나라도 ❌ → 완료 아님. In Progress 유지하고 어디까지 했는지 남긴다.
```

**부분 완료를 완료로 두는 것이 가장 위험하다.** 아무도 이어받지 않기 때문이다.

> **실제 사례(2026-08-05)**: BBE-50(A2 백필)이 `Done` 이었지만 백필은 실행된 적이 없었다. 붙어 있던 PR 은 "런북에 백필 단계 추가" = 문서였다. 이대로 개막했으면 **참가자 55명 화면이 빈 채로** 떴을 것이다.

## P5. 모호하면 멈춘다 — 추측으로 진행 금지
**지시가 모호하거나, 실측이 지시와 다르면 실행 전에 멈추고 묻는다.**

```
멈추고 물어야 하는 신호:
· 지시의 전제가 실측과 다르다        → "지시는 X 라는데 실측은 Y 입니다. 어느 쪽으로 갈까요"
· 같은 목적의 더 나은 방법이 보인다   → 대안을 근거와 함께 제시하고 판단을 받는다
· 되돌릴 수 없는 작업인데 확신이 없다 → 무조건 멈춘다
· 수강생 실데이터가 바뀐다           → 무조건 belie 승인(§0.7 화이트리스트)

멈추지 말아야 하는 것:
· 되돌릴 수 있는 결정  → 스스로 하고 근거·복구법을 기록(§0.7)
· 이미 답이 나온 것    → P6 참조
```

## P6. belie 에게 요구하기 전에 — 이미 끝난 일인지 확인
**같은 요구를 반복하는 것이 신뢰를 가장 빨리 깎는다.**

```
belie 액션을 요청하기 전 필수 확인:
□ 이 요청을 전에 한 적 있나?          → worklog·Linear 코멘트 검색
□ belie 가 이미 처리했을 가능성은?      → 실측으로 확인(설정값·배포 이력·파일 상태)
□ 실측 근거를 요청에 첨부했나?
□ belie 가 볼 화면·누를 버튼을 이름으로 적었나?  (belie 는 개발자가 아니다)
```

**근거 없는 재요청은 반려된다.**

> **실제 사례(2026-08-05)**: 토큰 재발급 요청이 **세 번** 나왔다. 실제로는 첫 번째에 이미 등록됐고, 배포 10회로 서버 주입까지 끝나 있었다. 확인만 했으면 반나절을 안 잃었다.

## P7. 제출 전 자기 리뷰 — 4렌즈
**작업을 끝냈다고 생각한 순간, 제출하지 말고 아래 4개로 자기 것을 공격한다.**

| 렌즈 | 자문 |
|---|---|
| **정확성** | 내가 쓴 숫자·경로·SHA 가 실제와 같은가? 하나라도 안 본 채 쓴 게 있나? |
| **완결성** | 수용 기준을 하나씩 짚었나? 빠뜨린 항목이 있나? |
| **파급** | 이 변경이 **다른 곳**을 깨뜨리나? 같은 함수를 쓰는 다른 화면은? 비파일럿 기수는? |
| **되돌리기** | 잘못됐을 때 어떻게 되돌리나? 그 방법을 적었나? |

**발견한 문제는 숨기지 말고 보고에 함께 적는다.** 나중에 남이 찾으면 더 비싸다.

## 사용 방법 — 단계 쪼개기

낮은 모델은 **한 번에 여러 단계를 주면 뒷부분을 흘린다.** 배차하는 쪽(반장·Cowork)은:

1. **한 번에 한 단계**를 준다. 결과를 받고 다음을 준다.
2. **답을 프롬프트에 박아준다.** "문서를 읽고 판단해라" 대신 필요한 내용을 발췌해 넣는다.
3. **금지사항을 맨 위에 명령형으로.** 이유는 뒤에 붙인다.
4. **출력 형식을 빈칸으로 준다.** 자유 서술은 누락을 부른다.

## 이 프로토콜이 실패하면
같은 실수가 **두 번** 나오면 그건 세션 잘못이 아니라 **이 문서의 잘못**이다(CLAUDE.md §0 하시모토). 프로토콜에 항목을 추가하거나, 아예 기계가 잡도록(린터·테스트·훅) 옮긴다.
