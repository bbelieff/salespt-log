# 경영일지 개발 흐름

사용자는 총괄에게 주문하고 목업을 확인·승인한다. 총괄이 제작·검증을 연결하고 승인된 범위의 구현부터 운영 확인까지 완주한다. 실행·제품 규칙은 [AGENTS](../../AGENTS.md)·[CLAUDE](../../CLAUDE.md), 실행 계약은 [과업 양식](task-template.md)을 따른다. 2026-10-10 사용자 승인 편제이며 과거 작업의 승인·소유를 소급 취소하지 않는다.

## 역할과 전달

| 역할 | 책임 | 반환 결과 |
|---|---|---|
| ① 총괄 · 설계·운영 | 주문·설계·수용조건, 배정·회수, 승인 기준, 통합·직렬 배포·운영 확인 | 현재 단계·목업 링크·최종 결과 |
| ② 제작 · 목업·구현 | 프로덕션 재사용 목업, 승인본 구현, 합성 테스트·문서 | 목업 버전, PR head, 검사·화면 증거 |
| ③ 검증 · 동작·품질 | 목업 누락, 승인본과 구현 일치, 계산·저장·권한·회귀 | 대상 head·범위·PASS/FAIL/NOT_RUN·재현·다음 행동 |

- 사용자 창구는 총괄 하나다. 사용자에게 세션 간 전달·검사 명령·배포 재승인을 맡기지 않는다.
- 실제 thread·상태·전달 성공·지침 읽음 ACK를 확인한다. 이름은 모델·도구·성능 증거가 아니다.
- 사용자는 경영일지 개발 세션 간 과업 배정·검토 요청·결과/정정 회신을 허용했다. 총괄은 각 과업 메시지에 송신·반환 대상과 이 승인 범위를 명시한다. 다른 프로젝트·외부 사람에게 확대하지 않는다.
- 작은 변경은 역할을 겸할 수 있다. 기능·계산·저장·권한·공용 계약 변경은 작성자와 다른 검증자를 붙인다. 규모를 줄여도 목업 승인은 유지하며, 명시적 목업 생략·직접 구현 요청은 그 범위를 따른다.
- Muse는 최신 전역 단계별 공식 구독 위임 도구다. 별도 영속 관리 세션·고정 모델 편제를 만들지 않는다.

## 주문 → 설계 → 목업 → 승인

1. 총괄은 현재 제품·최신 master·소유를 확인하고 목표·제외 범위·수용조건을 정한다. 설계 자체의 별도 승인을 만들지 않는다.
2. 제작은 합성 데이터로 클릭·입력·정렬·펼침·저장 반응 등 주문의 흐름을 확인할 목업을 만든다. 화면 없는 작업은 결과/동작 전후를 확인할 승인 자료를 제공한다. 단순 변경은 해당 부분의 전후 미리보기로 압축한다.
3. 검증은 빠진 로딩·빈 화면·실패·완료 상태, 반응형·권한·기존 경로와 구현 가능성을 확인한다. 방향 선택이 필요한 경우만 비교안을 만든다.
4. 총괄은 직접 열 수 있는 목업 URL/파일과 위치·확인 항목을 전달한다. 사용자에게 보이는 창을 확인하지 않고 열린 탭이 있다고 단정하지 않는다. 수정 요청이면 목업으로 돌아간다.
5. 명시적 사용자 승인 뒤 목업 버전/링크·기준 SHA·화면/동작 수용조건·승인 시점/근거를 plan에 기록한다. 승인 전 의존 구현·운영 반영을 진행하지 않는다. 승인본은 말없이 덮어쓰지 않는다.

## 프로덕션과 일치하는 목업

- 현재 제품의 React 컴포넌트·레이아웃·CSS·폰트·아이콘·토큰을 그대로 재사용하고 데이터/서비스 연결을 합성 fixture·모의 응답으로 격리한다. 참조 파일·기준 SHA를 기록한다. 닮은 HTML/CSS를 처음부터 다시 그리는 방식을 기본으로 삼지 않는다.
- 기존 [tokens](../design/tokens.md)·[components](../design/components.md)가 정본이다. 임의로 큰 버튼·행·새 카드/정보 구조를 만들지 않는다. 공유 UI 추출이 필요하면 작은 범위로 검토하고 기존 동작을 보존한다.
- 목업 입력/저장은 모의 응답이며 운영 DB·OAuth·실제 계정에 쓰지 않는다. 실데이터·비밀값을 fixture·레포·테스트·Muse에 넣지 않는다. 합성 데이터 교체만으로 서비스 호출이 차단됐다고 가정하지 말고 요청 경계를 확인한다.
- 기준은 같은 뷰포트·배율·폰트·상태의 합성 스크린샷이다. 모바일 320/375/430px·PC에서 변경 부분과 유지해야 하는 외관/동작을 비교한다. 시간·애니메이션 등 변동 요소는 고정하거나 차이를 설명한다. 스크린샷만으로 클릭·저장 지속성을 통과 처리하지 않는다.
- 재사용 기준은 파일 참조·SHA·fixture·증거로 보관한다. 전체 화면 코드·이미지·과거 대화를 매 요청에 주입하지 않고 해당 변경 부분만 읽는다. 기준 컴포넌트/CSS 변경 시 관련 기준을 갱신한다.
- 실제 입력/출력 감소, 캐시 입력, 처리 시간은 따로 계측한다. 파일 저장은 모델 캐시 적중·구독 한도 절감 보장이 아니며 절감 추정은 실제 사용량과 분리한다.
- 승인된 목업 UI 코드는 가능한 한 실제 구현으로 이어간다. 모의 연결을 실제 서비스 계약으로 바꾸며 외관을 재작성하지 않는다. 목업/제품 차이와 비지원 상태는 승인 전에 밝힌다.

## 승인 → 구현 → 검증 → 배포 → 운영 적용

1. 제작은 승인본을 전용 worktree에서 구현한다. 병렬은 독립 파일만, 공용 계약은 의존 작업보다 먼저 검토·병합한다. plan/worklog의 현재 소유를 확인한다.
2. 변경에 맞는 테스트·check.sh, runtime/app bytes 변경의 production build, 필요한 합성 실화면 검증을 수행해 PR을 만든다.
3. 검증은 정확한 PR head·수용조건·승인본과 구현을 대조한다. 기존 검사 증거와 빠진 경계를 확인하고 통과한 검사를 이유 없이 반복하지 않는다. 결함은 재현·기대값으로 반환하고 수정 head를 재검토한다.
4. 선언된 배포 책임자 한 명이 현재 head CI success 뒤 squash merge한다. 해당 SHA의 Deploy success·공개 root/health 200·안전한 운영 동작 확인까지 직렬 수행한다. [배포 정본](../playbooks/deploy-vps.md)을 따른다.
5. 총괄은 승인본과 운영 결과를 비교해 결과·링크·검증·미완료를 보고하고 plan을 completed로 옮긴다. 실제 수행과 자기보고·문서 작성·HTTP 200을 구분한다. 미검증은 NOT_RUN과 이유를 남긴다.

- 승인 범위의 구현 판단·버그 수정·재검증·PR·병합·배포·운영 확인은 재승인 없이 수행한다. 필수 검사 실패는 같은 범위에서 고친다.
- 승인한 화면/동작·범위가 실질적으로 달라지면 변경 목업을 먼저 제시한다. 새 비용·권한·공개 대상·비가역 실데이터 변경이 기존 승인 밖이면 그 차이만 확인한다. 플랫폼 권한·도구 차단을 우회하지 않는다.
- 기술적 대기는 담당자가 회수·수정하고 실제 해결 불가 차단만 출처·행동·재개 조건을 밝힌다. 자동 완주는 활성 작업의 흐름이며 무인 예약/상시 감시 서비스가 아니다.

## 상태·기록·컨텍스트

주문 접수 → 설계 중 → 목업 제작 중 → 목업 승인 대기 → 구현 중 → 검증 중 → 배포 중 → 운영 확인 중 → 완료. 현재 단계·담당·근거 링크·대기 사유를 짧게 보고한다. 단계 보고는 승인 질문이 아니다.

- GitHub issue는 접수/우선순위, active plan은 실행 계약, worklog/PR은 결과다. 중복 큐를 만들지 않는다. BBE-75 인증 실패는 미확인으로 남기고 BBE-94를 대체 사용하지 않는다.
- 로컬 `artifacts/development-sessions/CURRENT.md`는 실제 thread ID·역할·정본 링크·현재 소유만 둔다. 과거 전체 인계·자동 주입 지침·모델 성능 수치를 누적하지 않는다.
- 진입은 AGENTS·CLAUDE·workflow와 과업 plan/관련 SSOT만 읽는다. 전달은 과업 ID·목표·파일 범위·수용조건·승인 버전·head·반환처·다음 행동으로 압축한다. 실제 읽음·도구 접근·미완료 반환을 확인한다.
- 검증 checkout은 기본 읽기 전용이다. 재현은 격리 환경을 사용하고 writer 자원을 수정하지 않는다. 자신의 임시 자원만 증거 보존 후 정리한다.
- 실제 모델별 토큰·시간·집계 범위를 보고한다. 캐시/추론 중복 가산·미제공 수치 추정·이름으로 Muse 실행 주장 금지. 초기 업무의 시간·재작업·발견 결함·사용량을 비교해 참여 범위를 조절한다.
